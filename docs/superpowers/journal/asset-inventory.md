# Asset inventory: what the APK carries and where each piece can come from

Repo: digivice-ayn-thor, branch android-thor, HEAD 136d81fb, tree clean (122 commits after upstream base 89a6d647).
Everything I ran wrote only into scratchpad/inv/ (listed at the end). I removed the `__pycache__` folders my runs created in Tools/ (git status is clean again).
"Checked" = I ran it or read it. "Inferred" = reasoning, not verified.

## 0. What goes into the APK (checked)

- `Android/app/build.gradle.kts:43-47,91-103`: Gradle copies `Frontend/dist-handheld` to `assets/www/` and `Backend/Memory/Definitions` to `assets/definitions/`. Nothing else is bundled besides Kotlin code and the launcher icon (`Android/app/src/main/res/mipmap-*`, own icon, commit 136d81fb). `Android/core/src/test/resources/golden` is test only.
- `Backend/Memory/Definitions`: 35 JSON files, 164 KB, RAM addresses and `quest-conditions.json` (generated by `Tools/FieldData/generate_quest_conditions.py`). 30 of the files are upstream (89a6d647). Facts, can stay (not read file by file for text).
- dist-handheld is 71 MB: 1123 png, 279 webp, 80 svg, 317 js (4.08 MB), 1 woff2. The js is one 2.5 MB main chunk (`handheld-*.js`: every `src/database` json, en-US and pt-BR locales, the generated .ts tables), four 180 KB locale chunks (es/fr/de/it) and 312 tiny per-card chunks (the card PNGs, inlined as base64 because they are under Vite's 4 KB limit).
- Method for "reaches the bundle": for each source file I looked for its md5 among the files of dist-handheld/assets, or its base64/URL-encoded head inside the js/css. Every file of every folder marked "yes" below was found. So dist is in step with the current sources for those folders.
- Why so much arrives: `src/catalogs/image.catalog.ts:63-124` uses eager `import.meta.glob` for 12 folders, and 10 handheld files import `ImageCatalog` (battle-sheet, evolution-sheet, map-sheet, seabed-sheet, mobius-sheet, wiki-*). An eager glob puts the whole folder in the bundle even if no screen draws it. `src/catalogs/battle-image.catalog.ts` (battle/ folder) was split off in commit ad6df98f precisely so the handheld does not carry it.

## 2. TCG cards, and the other pictures

### TCG cards (checked)
- On the disc: `AAA/DAT/CARD/CARDPAK0.BIN`..`CARDPAK4.BIN` (LBA 1995, 2045, 2095, 2145, 2195; sizes 101120 x4 and 94800). In the decomp they are `STCRDDEK_FILE_CARDS` = file 0x7F6 and the next four (`include/cardgame/deck_editor.h:30`, EU), and `CardImage` in `include/engine/gfx.h:172`.
- Format: 64 cards per file, 1580 bytes each (= 0x62C): 12-byte header `{u8 color(1-6), ap, hp, kind, unused, points, level, pad, s16 rank, s16 comboCard}` then a 1568-byte TIM: 8-bit, 256-colour CLUT, 32x32 pixels. 316 cards in all (314 used by the app plus 2 blank).
- Match test: I decoded all 316 and matched each of the 314 PNGs of `Frontend/src/assets/cards` against them at offset (4,2) inside the 40x46 picture. All 314 match a distinct disc card; mean abs error 0.27/255 with 5->8 bit replicate (`(c<<3)|(c>>2)`, as `sprite.py` does), 1.76 with `c<<3`. The card id of `database/tcg/card.json` is 1000 + disc index (checked on 3: Agumon 1224 <-> 224, Airdramon 1212, Absolute Barrier 1038). The header gives AP/HP: Agumon header 5/3 = the "5/ 3" printed on its picture.
- Frame and strip: outside the art and strip the 40x46 pictures are identical per card colour (frame variance 0.04-0.11 across cards of one colour, 6 colours). So the missing pieces are 6 frame colours and the AP/HP digits, not 314 pictures. I did not locate them on the disc: the card UI is drawn by `CardDrawer` from sprite files (`STCDSPCS/TM.BIN` at 0x63E/0x642 EU, `CARDDATA.BIN` = `FILE_CARDGAME_TIMS` 0x25D); `STCDSPTM` holds 16-bit TIMs that `tim_to_rgba` does not read yet. Fallback: draw the frame and digits from a tiny embedded definition (a few hundred bytes of colours and a 3x5-type digit font), not game art. Needed work: ~60 lines to decode art, plus either the sprite sheet reader or the fallback.
- Result: "the same picture" is reproducible for the art (pixel exact up to the 5->8 bit rounding); the frame and strip are reproducible by one of the two ways above. `Design/build_cards.py` (86 lines) re-takes the digits from the cards themselves, so it must not run on-device unchanged.

### Field sprites that stand in for tamers, npcs, bosses, stores, duel-island, dri-agents (checked)
- Method: for each PNG, same alpha-trimmed size and same opaque count against all 2472 actor PNGs, then mean colour difference. 16/21 tamers, 10/10 npcs, 6/6 bosses, 1/1 stores, 2/2 duel-island and 8/8 dri-agents have a same-shape actor sprite with mean difference 1.5-4.0 per channel (not 0 because upstream used `c<<3`, `sprite.py` uses replicate). No match by shape for 5 tamers (Bob, Genji, Natsumi, Tomomi, Wong): different frame or edited, unresolved. The mapping name -> character id (`key1`) is not in the repo for these; it needs a table (about 50 entries).
- So these pictures are the game's field sprites: regenerable by `field_actors.py` + a name -> id table, with a 1-3% colour difference.

### Digievolutions, enemies (checked on a sample)
- The partner models are in the same fighter table as the enemies: `SMDLDATA.PRO` (file 0x1CC), 248 ids, 55 of them partners (kind < 0x3A, kind = line number of `ESDIGNAM`, e.g. kind 16 = Angemon). Partner `FighterInfo` is 0xC4 bytes (0x48 for enemies): `enemy_models.py` runs on it with `Fighters.enemy` pointed at `partners + index*0xC4`. I did that for one partner (model file `M020ANGE.BIN`): 0.08 s, 312x324, image in `scratchpad/inv/partner_angemon.png`; side by side with `digievolutions/Angemon.png` (`angemon_cmp.png`) it is the same character and same pose style, but the disc one is a PS1 3D render (flat textures, front view) and the app's one is an illustration. Close in subject, different in style. All 44 forms have a model (the table has 55 partners; I rendered one only).
- Enemies: the 3D render is already the app's picture (see table).

## 3. Text and data from the game inside the bundle

Disc text: `AAA/DAT/COUNTRY/{ENG,SPN,FRA,GER,ITA,JPN,USA}/` each has 50 files; file name prefix per language: ENG `ES`, SPN `SS`, FRA `FS`, GER `DS`, ITA `IS`, JPN `MS`, USA `US` + table name + `.BIN`.
Format (read from `ddw3/tools/ddw3-lang-file`, 798 lines of Rust in total, of which `codepoint.rs` 537): `u32 count`, `count` u32 offsets from file start, then null-terminated byte strings. Bytes are not ASCII: a game code table of 358 entries (232 single-byte: digits, A-Z at 0x0e-0x27, a-z at 0x28-0x41, hiragana/katakana from 0x42; 126 multi-byte: `01 xx` accents, `02 xx` controls such as end of line, `[clear]`, `[name]`, and 3-byte `02 05 nn` = `{n}` placeholders). The comment in `codepoint.rs` warns that some codes are locale dependent; I found no mismatch.
Check I ran (`scratchpad/inv/langtest.py`): a 25-line Python decoder using that table, applied to every `COUNTRY/<lang>` file that ddw3 has a TOML for (39 tables per language), compared string by string with ddw3's TOML: ENG 10833/10833, FRA 10833/10833, GER 10833/10833, ITA 10833/10833, SPN 10832/10833 (one string with unknown escapes prints differently), JPN 10847/10847, USA 10399/10399. So decoding is solved for all five European languages (and JPN/USA) with one table. The 11 `ESDMG*.BIN` story-script text files per language are not in ddw3's lang_file tree (different folder) and I did not decode them; the app does not use them.
Sizes on the disc of the tables the app uses (17 tables + 10 TALK files): ENG 62 KB + 379 KB, SPN 65 + 366, FRA 64 + 388, GER 61 + 368, ITA 65 + 341; about 2.2 MB across the five languages (not all needed).

## 4. What the extractors read at generation time

From `dw3_decomp` (C sources parsed as text; `DW3_DECOMP`):
- `src/engine/file/file_table.c`: `FILE_SECTORS[2382]` (EU). Checked: the same 2382 int32 sit in the disc executable `SLES_039.36` (LBA 24, 923648 bytes) at file offset 0x3576c (a 24-byte pattern search of the first 6 entries found one hit), so this table does not have to be shipped: read it from the exe.
- `src/field/field_mode/data/fieldstg.c`: `FIELDSTG_stages` (mode, file, WSTAG start), `FIELDSTG_fileEntries` (character -> sprite pack + table), `FIELDSTG_actorWidths`, `FIELDSTG_enemies`. Used by `actors.py`, `parse_stages.py`, `field_actors.py`, `generate_*`.
- `src/field/stages/**/wstagNNN.c`: 295 files, 5.3 MB of C. Stage name (first comment), `mapFile`, setup colour, `stageObjects[]`, slots/places, talk entries, scripts. `render/stagedef.py` and `parse_stages.py` extract it with a small preprocessor and regexes. I ran `stagedef.load_stage` for all of them: 294 stages parsed, JSON 1.9 MB (106 KB deflated) = the table the map renderer would need as data.
- `src/menus/field_menu/helpers.c` (`STSTATUS_spots`, `STSTATUS_towns` for the world map), `src/engine/game/items.c` (item frames, names ids), `digimon.c`, `events.c`, `include/engine/story.h`, `game_state.h`, `field/field_map.h`, `field_actors.py` scans all `src/**/*.c`, `config/eu/symbols.txt`.
From `ddw3` (`DW3_DDW3`):
- `iso/dw2003-bootstrap/lbas.toml`: file index -> name (`SnnnPACK_BIN`), used by `dwr.py`, `actors.py`, `parse_stages.py`, `generate_exits.py`. Replaceable by ISO9660 lookup of the sector from the exe's file table (`discfs.py`/`Files.by_lba` already does that for the other scripts).
- `lang_file/dw2003/<lang>/*.toml`: decoded text, by `generate_locales.py`, `generate_techniques.py`, `generate_seabed.py` (esitmnam), `item_icons.py`, `field_actors.py` (estalk). Replace with the on-device decoder of section 3 (the toml is only the decoded form of the disc `.BIN`).
- Formats (pack, RLEN, TIM, map-tile): already re-implemented in `mapx.py`, `sprite.py`, `world_map.py`; no ddw3 file is read at run time for them.
What must become a data table inside the app (inferred from the above):
1. Character code table (358 entries, about 4 KB).
2. Key -> (table, line index) for the app's translated keys (today the generator matches English strings with difflib, which is only possible with the English text at hand; I did not measure the table size, about 1365 + 2066 lines in order of 40 KB).
3. Stage table for map rendering (about 106 KB deflated, 294 stages), or parse the overlays `AAA/PRO/WSTAGnnn.BIN` (318 files, 2.2 MB, they hold the compiled copies of these tables; needs symbol offsets from `config/eu/symbols.txt`; inferred).
4. Character id -> sprite pack and table, actor widths (a few KB), name -> character id for tamers/npcs.
5. World map spots/towns (small), item frame table (already in `item-icons.ts`), partner/enemy ids (already in database json).
6. Already generated facts (map-exits, seabed-docks, server-copies, field-actors frames/roles, game-techniques numbers, item-icons) stay as they are, minus their name strings if you want no game text in the APK.

## 5. Disc access

- All Python tools read a `.iso` of 2048-byte user-data sectors: `iso.py:Iso.sector` seeks `lba*2048` (`iso.py`, 39 lines) and `discfs.py` (30 lines) walks the ISO9660 path table and directory records to give name, LBA, size (2385 files). The "file table" of the game (`FILE_SECTORS`) is a separate array read from the decomp today and from the exe (above), mapped to names through the ISO listing.
- BIN/CUE: the local cue is `FILE "game.bin" BINARY / TRACK 01 MODE2/2352 / INDEX 01 00:00:00` (single data track, no audio, no pregap). For a data file sector `n`, read 2048 bytes at `n*2352 + 24` (12 sync + 4 header + 8 subheader) for Mode 2 Form 1. Form 2 sectors carry 2324 bytes at +24 with no EDC; they are only used by the movies. Inferred: all files these tools read (DAT, PRO, exe, SYSTEM.CNF) are plain Form 1 files. Not checked on a raw BIN: I do not have the bin, the iso here is already cooked (294280 sectors x 2048).
- XA/multi-mode: 14 `AAA/STR/MOVIE*.STR` (274 MB, 46% of the disc) are video (interleaved Form 1/2) and `DUMMY.` (35 MB) is padding; none is needed. No `.XA` file; sound is in `AAA/DAT/SOUND/*/` as plain files. `ddw3-cdrom-xa` exists in ddw3's tools but nothing here needs it.
- CHD: not checked (no sample). CHD stores 2448-byte frames (2352 + 96 subcode) in compressed hunks (zlib/lzma/huff/flac for CD); a reader needs libchdr (C, via NDK) or a port, then the same `n*2352+24` math inside decompressed hunks; metadata `CHT2` gives the tracks. Plain `.iso` (2048) and `.bin` are easy; CHD is the heavy one.
- Region check: the disc must be EU (`SLES-03936`): every file table is EU (`FILE_SECTORS[2382]`); US/JP tables differ (`file_table.c:8,838,1737`).
